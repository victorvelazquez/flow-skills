# Simplify Flow Branch explicit selection

## Goal

An explicit `/flow-branch <branch>` invocation or a branch chosen from its numbered inventory authorizes one safe checkout and fast-forward-only update without a redundant `ask-pull` confirmation. Bare `/flow-branch` still requests a branch selection. Deletion and force-deletion remain separate, branch-specific human decisions.

## Scope and safety

- Reuse the existing single named Pi/OpenCode agents and package-relative Flow Branch runtime. Do not add agents, custom TUI gates, or new branch-policy machinery.
- For a number from the displayed inventory, map its `index` only through that listing's `branches` array, never through the independently ordered `allBranches`. Use the exact name with the selector sharing the direct route's safety checks. The one-token `dev`/`develop` aliases deliberately prefer `development` even when exact names exist; do not forward numbered selections through aliases. Validate the name as data; never interpolate input as shell syntax. Missing or stale selections stop, not guess. Numeric deletion requests use the same displayed-index mapping, then require separate confirmation naming the exact deletion candidates.
- Keep runtime fetch, clean-worktree, remote tracking, protected-branch, divergence, and fast-forward-only safeguards. Leave the runtime's interactive `ask-pull` compatibility path intact unless a focused check proves it can be removed safely; the adapters should no longer require it for explicit checkout selection.
- `/flow-branch` does not authorize deletion. Preserve separate deletion confirmation and per-branch `ask-force-delete`; do not broaden OpenCode/Pi permissions or claim that a host-enforced dialog can be bypassed.
- Do not execute live checkout, fetch, pull, delete, push, PR, merge, or Jira as a verification probe. Tests may use temporary repositories. Preserve unrelated files and OpenSpec history.
